# Synthetic fixture evaluation

Measured through the real browser pipeline on the four generated PNG fixtures. These results are a smoke evaluation, not a precision/recall or real-world accuracy benchmark. The machine-readable observations and processing times are in [fixture-results.json](fixture-results.json); timings depend on device, warm caches, and concurrent work.

| Fixture | Findings observed | Connected groups |
| --- | --- | --- |
| Developer terminal | 1 email, 1 possible credential assignment, 1 URL context, 1 IP context | 1 developer group |
| Travel ticket | 1 decoded QR, 1 QR email, 2 booking references (OCR + QR), 5 travel-context findings (OCR + QR) | 2 spatial travel groups |
| Shopping receipt | 1 email, 1 contextual phone, 1 order ID, 1 uncertain address | 1 delivery group |
| Control image | 1 public URL context | 0 groups |

Both OCR and QR stages completed for all four fixtures. The control produced no credential, phone, address, order or booking findings; ordinary long numbers remained unflagged. URL context is intentionally visible but unselected, not classified as a dangerous secret.

## Misses and limitations observed

- OCR changed part of the developer URL (`/v1` was read as `/v1l`) in the observed run. The URL rule still detected context, but exact evidence was imperfect. The engine does not silently “correct” it.
- OCR picked up QR-like visual fragments near travel text in a departure-line match. The multiword boxes can include those fragments. This is a context overmatch; review the highlighted words. The QR decoder independently read the intended payload correctly.
- The fictional passenger name is only shown inside the decoded QR payload. There is no standalone name detector. Covering the whole QR protects this payload; the app does not claim to identify names generally.
- Travel evidence produced two spatial groups because the text panel and QR panel have different proximity connections. These are evidence groups, not two independent incidents, and are not added into a risk score.
- Receipt address detection covers the labelled line only, not arbitrary multiline or unlabelled addresses. The phone fixture uses a clearly nonfunctional all-zero synthetic international number and tests string-shape detection, not number allocation.

## Artifact checks

Browser integration checks independently inspect flattened PNG pixels: manually selected regions become `[0,0,0,255]`, an unselected source pixel is unchanged, and developer export retains 1200×620 dimensions. Independent ZXing decoding reads one QR in the original travel fixture and zero in its exported redacted version. These checks apply to these fixtures and selections, not all images or every scanner.

The failure test deliberately blocks the local OCR language file and requires a visible partial-analysis warning. Other integration checks exercise stale result invalidation and clear during delayed demo loading. A mobile control scan runs while third-party HTTP requests are blocked and checks for horizontal overflow and localStorage writes.

Additional regression assets `railway.png` and `thorough.png` are generated by the same script but are not part of the four-fixture table. The thorough integration test uses an equivalent 3200×900 synthetic raster with overlapping email evidence: it processes two native tiles plus an overview, yields one merged email finding, restores its original-image coordinates, and exports 3200×900 pixels. Failed-tile and cancellation tests exercise this same real pipeline. This does not measure comparative OCR accuracy or a guaranteed gain from thorough scanning.
